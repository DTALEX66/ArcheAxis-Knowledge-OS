## 1. 最高架构原则

### 1.1 AAOS 是通用能力权威

凡是可以通用、可复用的能力，以 AAOS 为主要归属：

- 统一记忆管理和权威存储。
- 用户偏好与长期知识。
- 知识来源、引用、版本和学习记录。
- 模型适配、模型路由与用量管理。
- 通用 ASR、TTS、音频传输和感知服务。
- 会话与任务生命周期。
- 工具调用、权限审批、审计及执行回执。
- 用户资产、配置、持久化与版本迁移。

星栖只拥有角色领域中真正特殊的逻辑：

- 人格和角色配置。
- 陪伴行为与关系互动规则。
- 角色情绪表达和行为状态编排。
- 形象、声音风格、动作、表情及口型协调。
- 角色化上下文呈现。
- 多种显示形态的协调与切换。

即使某项通用能力首先由星栖研发，最终也应该抽象成 AAOS 可复用模块。

**不得为星栖长期维护第二套独立记忆主库、模型管理中心、任务引擎或正式产品前端。**

### 1.2 一个权威数据写入链路

遵循 AAOS 当前有效架构与合同。

目前已经确认的技术方向是：

- Tauri 2
- React + TypeScript + Vite
- Rust Core：权威业务写入
- SQLite / CAS：权威记录和资产
- Python workers：按需执行隔离计算任务

以上是 AAOS 现行方向，不意味着星栖必须立即拥有所有后端组件。

星栖通过有类型、有版本、有权限的 Host Adapter 与 AAOS 通信。

不得直接写 AAOS 的 SQLite、CAS、记忆索引或知识状态。

角色对话产生的记忆只可以作为可治理的候选数据，通过 AAOS 正式接口记录、修改、撤销或删除。

对于虚构剧情、人设状态、私人对话和已验证事实，必须建立明确类型和权限区分。

### 1.3 一个正式前端，多种表现形式

最终星栖必须能融入 AAOS 正式前端。

允许独立开发期建立 Dev Host 或 Storybook 类测试宿主，但它只能是开发工具，不能演化为第二个需要长期维护的正式产品前端。

角色展示层必须支持逐步扩展：

`embedded`：嵌入 AAOS 页面。

`panel`：侧栏角色与对话。

`floating`：独立悬浮角色窗口。

`pet`：低干扰桌面宠物。

`voice-only`：仅保留语音和状态反馈。

这些模式使用一致的角色身份、会话与任务状态。

不要为每种模式复制一套业务逻辑。

## 4. 建立星栖的最小可扩展模块

根据真实仓库现状决定目录，不机械复制以下结构。

建议至少形成明确的逻辑边界：

**Astryn Contracts**

定义角色、会话、表现状态、Host 能力和权限契约。

**Astryn Companion**

管理人格、角色配置、互动策略、场景切换和表达行为。

**Astryn Interaction**

管理输入、输出、流式响应、打断、事件时序与交互状态机。

**Astryn Avatar**

管理角色呈现、表情、动作、口型与可替换的渲染驱动。

**Astryn Presentation**

提供可复用 React UI，能够在不同 AAOS 展示形态中挂载。

**Astryn AAOS Adapter**

只通过授权 Host API 调用统一服务，不绕过 Core。

**Astryn Dev Host**

用于独立运行和测试。默认使用隔离合成数据；可通过配置切换到真实受支持的模型/宿主接口。

这些是模块责任，不要求首版创建七个 npm 包、七个进程或七个数据库。

以最小可维护结构实现，避免过度微服务化。

### 必须定义的核心接口

建立稳定、可测试的接口或等价契约：

- `AstrynHostPort`：AAOS 宿主能力。
- `AstrynConversationPort`：会话与流式对话。
- `AstrynMemoryPort`：AAOS 记忆的授权访问。
- `AstrynActionPort`：任务请求、审批、状态回执。
- `AstrynContextPort`：获准获取当前文档、选择内容和任务上下文。
- `AstrynAvatarRenderer`：可替换角色表现驱动。
- `AstrynPresentationMode`：多形态显示。
- `AstrynCharacterProfile`：角色身份与表现配置。

接口命名可以调整，但责任和数据边界不可缺失。

特别要求：

所有任务状态必须来自真实系统事件，不得由大模型猜测任务完成。

流式事件应包含会话身份、关联任务、事件序号或版本，能够处理过期事件、取消、重复响应和断线恢复。

## 5. 第一个可运行闭环：M0

本次必须尽可能完成一个真实、可演示、可测试的纵向功能切片。

不要第一轮就实现整套 3D 世界、复杂自主 Agent、跨应用控制和多人物社区。

M0 的目标：

**用户打开星栖开发宿主，看到小栖；可以与她实际交互；角色根据真实交互状态变化；一套明确的适配契约可以连接 AAOS。**

### M0-A：真实角色显示

实现一个原创的“小栖”初始视觉角色。

首版可以使用自研 2D/SVG/Canvas 角色与轻量动画，后续通过渲染接口替换为合规 Live2D、VRM 或 3D 模型。

不要直接复制未经授权的成品角色模型，也不要用纯文本框冒充完整数字人。

首版角色至少应有：

- 待机状态。
- 正在聆听或输入状态。
- 正在思考状态。
- 正在回复状态。
- 出错或被打断状态。

表情和动作必须和真实事件连接。

优先保证稳定、流畅和低资源占用。

### M0-B：真实对话

实现可操作的文本会话。

优先使用已存在的 AAOS 统一模型接口。

如果 AAOS 接口暂时不可接通，允许建立**仅开发环境使用**的标准兼容模型适配器，用于验证真实请求与流式回复；后续由 AAOS 接管模型管理。

开发宿主不能在浏览器源码中暴露 API Key。

当没有配置可用模型时，必须明确显示模型不可用，不能把脚本回复冒充真实 AI。

角色对话需要具备可维护的身份、表达风格和上下文管理，不能只依赖一段不可配置的大提示词。

### M0-C：状态驱动行为

建立明确的角色交互状态机，例如：

`idle / listening / thinking / speaking / executing / awaiting_approval / completed / failed / interrupted`

其中任务完成、失败和审批状态只能由相应权威回执触发。

允许角色表达情绪和个性，但不得捏造系统状态。

验证多次请求、取消、打断、组件卸载和迟到事件，不出现错误状态串台。

### M0-D：记忆边界

实现 AAOS 统一记忆访问接口的最小契约及测试。

不得新建正式长期记忆数据库。

独立测试环境允许使用进程内合成数据或可销毁测试夹具，不将其当作第二套生产记忆库。

验证：

- 用户偏好只能从获准的作用域读取。
- 私密陪伴内容不能自动进入其他业务模块。
- 角色虚构经历不能被标记为真实知识。
- 模型生成的记忆必须经过可治理的候选处理。
- 用户未来可查看、编辑和删除相关记忆。

如果 AAOS 的实际记忆 API 尚不存在，清晰标记 `BLOCKED_BY_HOST_CONTRACT`，不要伪造已集成状态。

### M0-E：AAOS 上下文契约

设计一条最小真实集成场景：

用户在 AAOS 选中一段文字，小栖获得授权后的选中内容，解释其含义，并在可能时提供 AAOS 的真实来源标识。

当前不能直接接通时，可用明确标注的合成文档夹具完成契约测试，不得假装已经访问真实知识库。

确保以后能够替换为 AAOS 原生上下文，无需重写角色 UI。

### M0-F：可运行开发宿主

提供可复现的本地启动方法。

能够启动开发页面、进行角色交互、观察状态变化、切换基础角色呈现状态、执行测试并查看真实错误。

测试宿主应当可单独运行，但不是第二个正式产品。

## 7. 隐私、授权与资源控制

星栖可以有情感温度和角色表达，但必须明确是 AI。

用户应能关闭主动提醒、语音输入、感知能力和角色显示。

不得默认常驻录音、摄像头监控、屏幕采集或执行系统命令。

涉及删除文件、修改项目、发送外部消息、购买、运行高风险命令等行为时，必须使用 AAOS 统一授权机制。

角色身份不能提升操作权限。

禁止把私人会话、记忆、截图、声音样本、密钥和未经授权的模型资产提交到 Git。

优先使用本地可运行、成本可控的模块和已有模型接口；不要未经核对就下载大模型、安装大型运行时、调用付费 API 或启动常驻服务。

不要为了视觉演示牺牲 AAOS 现有性能和稳定性。

## 9. 首轮必须满足的验收门槛

至少检查以下场景：

- 已存在的 ASTRYN 仓库与远端没有被错误重建。
- 开发宿主可按文档启动。
- 能看到小栖的实际角色画面。
- 至少一种角色动作或表情由真实交互事件驱动。
- 文本输入能够在配置真实模型时得到真实回复。
- 模型缺失、网络失败或调用失败时明确报错。
- 取消或快速切换对话不会产生旧回复串台。
- 角色的任务完成反馈不能由语言模型伪造。
- AAOS Host Adapter 具备可测试的类型契约。
- 正式记忆没有被复制到另一套长期数据库。
- 角色 UI 没有直接操作 AAOS 权威数据库。
- 没有默认启用麦克风、摄像头和全屏读取。
- 前端构建和相关测试必须实际运行。
- 没有硬编码密钥、未经许可的模型或角色素材。
- AAOS 正式工作树、运行状态和原有任务没有被擅自修改。

对未达到的项目使用 `PARTIAL / BLOCKED / NOT_TESTED / FAIL` 等明确状态，并解释真实原因。

不得用“完成设计”“实现占位接口”或“将来可以接入”冒充实际功能通过。

## 10. GitHub 与交付约束

所有修改首先落在 ASTRYN 已有本地仓库。

保护现有 dirty 文件、未跟踪文件及用户数据。

不执行 `reset --hard`、`clean -fd`、强制推送或未经批准的批量删除。

可在安全的新分支中进行功能开发。

提交时只暂存本次确实属于任务范围的文件。没有明确远端交付授权时，先提供待提交变更、测试结果和拟执行的 Git 命令，不自动推送、合并或发布。

不在 AAOS 仓库另建与其现有任务队列竞争的“唯一主计划”。
