## 3. ⚠️ 但宿主监管下的写入，**一样 403**

```json
"host_supervised_write": {"status": 403,
                         "body": "{\"detail\":\"desktop write authorization rejected\"}"}
```

**这否掉了我第 111 轮的推断。** 我当时写：

> 「写入授权需要真正的桌面父进程管道握手 —— 而独立启动时那条管道不存在。」

**本轮宿主确实建立并监管着那条管道，写入仍然被拒。**
**所以「缺管道」不是原因。**（那里我标的是「推断」，现在它被实测否定 ✓）

## 4. 更可能的原因：**请求必须携带宿主签发的凭据**

线索来自第 105 轮的 grep —— 源码里出现过这样的请求头写法：

```
"x-archeaxis-launch-token: {TOKEN}\r\n"
```

**即：客户端要在请求头里带上启动令牌。** 而：

| 事实 | 后果 |
| --- | --- |
| 令牌由**宿主**生成并传给后端 | **外部探针无从得知** |
| 前端由宿主启动、能拿到令牌 | **所以前端能写，我不能** |

**这是一个健全的设计** —— 写操作绑定在宿主签发的凭据上。

**但它的直接后果是**：**外部探针无法完成写入**。

## 5. 因此「读写闭环」的测法要再改一次

| 测法 | 可行性 |
| --- | --- |
| ❌ 独立启动后写 | 403（第 111 轮） |
| ❌ **宿主监管下由外部探针写** | **403（本轮）** |
| ✅ **由应用自己的前端写** | **只有它持有令牌** |

**即：读写闭环必须走界面操作**（或宿主自身的 IPC），**不能从外部 HTTP 探针完成。**

**这不是我该绕过的限制** —— 它是产品有意的授权边界。
