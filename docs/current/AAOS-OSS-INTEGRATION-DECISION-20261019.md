## 三、接入形式的选择

以下是接入决策规则，**不是这些扩展机制均已实现的声明**。

| 形式 | 适合的能力 | 产品呈现与工程边界 |
| --- | --- | --- |
| 核心实现／已有模块适配 | 原件、版本、权限、持久化、核心导航与图谱基础交互 | 只有核心业务必要部分进入主干；Rust Core 保持唯一 SQLite/CAS 写者 |
| 模板／能力资产 | 课程大纲、研究流程、教学脚本、评估量规、可复用展示配置 | 在原有业务入口选择模板；模板是版本化数据，不能自行取得模型、网络、执行或写入权限 |
| 格式／协议适配器 | 外部课程、图谱或其他标准数据交换 | 转成现有领域对象；固定格式版本、保留原件与转换损失；不新增一个供体品牌空间 |
| 可选插件／隔离 worker | 非核心、较重、有独立依赖或平台约束的引擎 | 按需启用；通过有限合同调用，保留取消、超时、失败和退出。未安装就显示不可用，不随主包复制整套环境 |
| 技能／工作流 | 有明确输入输出、步骤、提示与人工确认的组合能力 | 在已有 AI 资产或业务任务中调用；复用既有模型选择与授权。开发工具 Skills 和产品技能分别登记 |
| MCP／既有 API、CLI、sidecar | 能稳定隔离的外部工具或服务能力 | 优先已有、范围有限的接口；先只读或预览，再按明确授权写入。MCP 是连接协议，不能代替 UI 渲染、数据合同或安装验收 |
| 设计参考／独立实现 | 无可用代码许可、完整产品不适配，但交互行为有价值 | 从公开行为及独立规格实现，建立自己的测试；不能复制未授权源码、资产或绕过付费服务限制 |
| 未来蓝图 | 当前收益不足以覆盖复杂度，或依赖尚未满足 | 留下能力目标、依赖、恢复条件和来源；不显示可用按钮，不删除 binding_core／binding_long_term 目标 |

选择顺序：先核对已有实现与可复用合同；能用模板或现有适配器解决的，不新增常驻服务；需要独立环境的隔离为可选能力；只有稳定、确有必要的交互进入产品主干。协议名本身不决定质量，简单的现有 API 可优于新建 MCP 服务。

## 四、重复、冲突与许可处理

1. 按“用户任务＋输入输出＋数据身份＋副作用”判断重复，而非按项目名称。一个能力允许多个可选实现，正常路径只保留一个明确默认入口。
2. 比较实际效果、数据保真、取消与失败恢复、无障碍、性能、离线能力、许可、依赖和维护成本；以同一任务条件验证择优。不因截图好看或测试数多直接替换现有实现。
3. 合并时保留来源与 ID 映射、旧引用可解析性、原件、版本及回退；数据不能自动跨来源合并，冲突不能静默覆盖。替换后验证原有闭环与新能力，再逐对象退役冗余。
4. 允许内容降级必须明确列出损失、让用户选择并保存转换报告；不能静默把完整课件变成标题列表。候选、未核验、失败、未知与成功保持区别。
5. 先查固定版本的实际许可与资产条款。MIT 等许可代码的复用保留应有声明；“商业使用”不自动表示收费。只有收费或许可条件不适合时，再比较公开接口、替代实现、独立自研或延期。
6. 独立自研从公开行为、标准与任务规格出发；未授权源码、品牌素材、模型权重和收费服务不能因为“复刻”获得使用或分发资格。过于复杂或无法合理独立实现的，进入第七节，不硬做低保真替代冒充完成。

## 九、后续 Owner 决定：强底座、内置能力市场与模型分层

### 直接来源与替代关系

Owner 在本文件初稿之后明确：
