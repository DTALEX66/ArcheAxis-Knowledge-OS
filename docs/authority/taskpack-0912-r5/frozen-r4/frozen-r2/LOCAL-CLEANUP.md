# X14：本地仓库 50 多 GB 保全与清理

用户已要求把前两天的清理任务并入。本文件给本地执行器使用；云端本轮没有访问用户 D 盘、停止其进程、移动或删除实际文件。

## 1. 先纠正旧账

旧报告称总量 56.6GB，列出 `.hermes` 42.86、src-tauri 5.18、desktop 4.91、target 1.80、.venv 0.86、apps 0.68GB。这六项相加为 56.29GB，并非报告另一处所写的 55.29GB；目录值还可能混合父目录和子目录口径。`.hermes` 明确混有会话/补丁/证据，不能归为全部可再生。

这些是历史自报值，不能当今天的测量或可删清单。使用字节统一计量，显示 GiB（除以 1024³），父子目录不重复加总。文件逻辑大小、硬链接唯一对象大小、实际磁盘可用空间分开，不能承诺一定回收某个 GB 数。

## 2. 执行顺序

### 第一步：停止继续增长（X01）

- 所有项目运行/测试/浏览器/打包入口改为声明的 `.project-local` 路径；短路径例外单独验证。
- 只暂停本次清理涉及的、已确认属于该项目的构建/推理/浏览器进程，不杀其他软件进程。
- 不迁移 CODEX/DSH/HERMES 自身的安装、会话、技能和全局缓存；不把 DSH 安装目录当 ArcheAxis 根目录。

### 第二步：只读计量与归属核对

将本包放在指定项目内。使用项目已有 Python 解释器，不为运行盘点器重装环境：

```powershell
python .\docs\authority\taskpack-0907-reuse-first\audit_local_storage.py --repo .
```

脚本在主 checkout 根运行，默认在项目内生成一个新盘点目录，包含逐文件清单、目录分类合计和最大文件。先确认输出被 Git 忽略；否则退出，要求完成 X01。不会跟随 symlink/junction/reparse point，不访问 E 盘，不删除数据，不读取被盘点文件正文，不扫描项目外部。linked worktree 的共享 Git 元数据不在扫描范围，须回到主 checkout 盘点。候选分类只用于审查，不是删除授权。暂停写入后运行；这不是文件系统快照或操作系统沙箱，Windows reparse 行为仍须在本机验证。

记录运行任务和软件的占用、构建/解析器锁文件、Git 修改状态。必要时记录开始/结束卷剩余空间，但不把期间其他进程造成的变化计入本次收益。

### 第三步：先保全不可再生内容

| 目录/材料 | 处理 |
|---|---|
| `.git`、源码、锁文件、契约、配置、测试、历史蓝图 | 保留，不属于缓存 |
| 真实知识库、原件、笔记、学习/机器反馈、数据库和附件 | 永久产品资产；保留，需迁移时走数据迁移任务 |
| `.hermes` 唯一会话、未合入 patch、收据、来源证据、唯一模型配置/自建数据 | 先语义检查、校验哈希并归档；不要依文件夹名判定可删 |
| `.hermes` 中下载包、临时站点副本、重复环境 | 对照来源、哈希、引用和重建方式后才分类 |
| 模型权重 | 默认保留当前模型及必要回退；只清重复或明确不用且可重取的对象，记录 revision/许可和获取方式 |
| OS/软件外部目录、链接目标 | 仅登记；不能因为名字相近就跨仓/跨盘清理 |

私人会话和用户内容不得复制到 Git 的 docs。只将脱敏索引与必要摘要入仓；完整归档保留在受控私有位置。盘点输出本身也是私有运行材料。

不要为清理复制整套 42GB 内容。先识别唯一项、重复项及文件引用；同卷保全移动必须有清单和回滚，跨卷移动不在默认授权范围内。

### 第四步：按清单清理已确认可再生的对象

优先处理 `target`、旧 `src-tauri/target`、`desktop/src-tauri/target`、旧 `desktop/node_modules`、已失效的 C# bin/obj、重复构建/测试临时副本。`.venv` 只有在依赖锁定、无唯一修改、能够用已有环境重建且不破坏正在使用的工具时才处理。

对每个候选记录精确路径、字节、Git 跟踪情况、归属、用途、最后使用、重建命令与版本、保留引用、清理动作。停止占用后执行现有授权覆盖的清理；已明确授权且验证为可再生的缓存不需要反复问用户。未知内容、唯一历史或真实数据库不纳入自动清理。

优先用工具自身的 clean 或已核对的精确目录清单；禁止 `git clean -xfd`、全仓递归删除、整体删除 `.hermes`/`.project-local`、删除全部模型或强制关闭所有软件。源码目录的父级不能因为包含 target 就整体删。

对可再生缓存，回滚是按锁文件重建；对需保全的材料，回滚是已验证副本/原位置恢复。二者不能混写成“都可重新下载”。

### 第五步：验证与持续控制

重新运行同一盘点器，对比同一口径：开始/结束字节、已删对象合计、实际剩余大目录、未知项与保留原因。再执行当前可用的启动、关键解析、模型识别和最小受影响构建，证明没清掉运行依赖。

固定当前开发环境和当前模型，不同时缓存所有上游/所有构建变体；运行产物按任务归属和保留标记淘汰。闭环初次跑通后实测正常峰值，设置可调容量预算和提示，不以任意硬配额阻断用户数据保存。

## 3. 清理完成的必要证据

- 清理前后逐文件索引与统一字节汇总。
- 精确删除/移动清单、保全哈希、占用处理和重建/回滚方式。
- 已释放空间与仍保留的最大目录，不用旧报告估算充当实测。
- 源码/Git/用户库未丢失；`.hermes` 在新任务后不再增长；实际启动/受影响能力仍通过。
- 若真实本地机器不可用，状态只能 BLOCKED_RESOURCE，不能因为云端给出了本文件就写完成。
