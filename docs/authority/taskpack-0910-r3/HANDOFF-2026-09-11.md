### 6. What the next session should know (the lessons that cost the most)

- **Run the whole Python suite, not the file you touched.** Round 90's two new tests passed alone
  and failed in the suite because they inherited the working tree's dirtiness. Round 87's defects
  were found the same way.
- **A gate green in one working tree is not a gate that runs in a clone.** Round 93: the
  difference was exactly one ignored receipt, and it had only ever been asserted in prose.
- **Measure the engine before designing around it.** Round 89's first design ordered blocks and
  would never have worked (the engine merges a whole row into one block); round 91's first design
  trusted the engine's line ids and reordered two words of one row; and a three-run probe caught a
  resume bug that a two-run test could not.
- **The stdio protocol is one JSON envelope per line** — engine chatter must be captured into the
  receipt, never printed. Staging is content-addressed, so workers dispatch on the file **suffix**
  their media type implies.
- **Receipt validation is strict**: canonical line anchors over the projected text, `covered` and
  `total` supplied together, `total` equal to the line count.
- **Commit with `git commit -F <file>`** for long messages: a quote in a message once mangled the
  command and silently skipped the commit.
- **A published number must be re-derived somewhere** or it rots; that is why the path record
  carries `measured_at_commit` and why three of this session's commits are just refreshes.
- **Checking that a command's script exists is not checking that the command runs.** Round 96
  executed all twenty recorded evidence commands for the first time: thirteen passed, six were
  covered by the full workspace run, and one was refused by design. It found two defects that no
  amount of reading had found.
- **Documenting a held-out evaluation destroys it.** The same audit found that a ledger row and a
  handoff section quoting two held-out values had made the corpus "seen", so the probe refused -
  and that the probe also counted **its own source file** as a tracked file. It had passed in
  round 87 only because it ran before being committed. The corpus is rotated, the values appear in
  no tracked file, and `tests/test_unseen_evaluation.py` now enforces the property in the suite.
- **Never write a corpus value twice.** The audit also found `main()` still holding literal copies
  of the old values, so after the rotation the "human correction" corrected nothing. Values are
  read from the corpus everywhere now, and a test asserts the correction really changes the value.
- **Running a recorded command is not the same as it working, and running it needs a shell's
  quirks.** Round 97 turned that audit into `scripts/check_evidence_commands.py` and found four
  more defects in the checker itself, all by executing it: Windows cannot start a `.bat` directly
  (it needs `cmd /c`); `cmd` rejects the forward slashes the index uses; the cargo runner needs
  **both** `ARCHEAXIS_RUST_TOOLCHAINS` and `ARCHEAXIS_MSVC_VCVARS` (without the second it dies at
  the C linker with exit 101); and reading one output stream hides the runner's own named refusal
  behind shell wording. All twenty recorded commands now exit 0 here.
- **A claim measured in your working tree is not a claim about a clone.** Round 98 ran the suite
  in a fresh clone and found 112 failures in 27 legacy test files that depend on untracked local
  assets; the handoff had been asserting clone-reproducibility for rounds. Run the claim where it
  claims to hold, or say where it was measured.
- **A prerequisite is not a failure, and a checker must know the difference.** The same round
  taught the command checker to report "no build here yet", "no Rust toolchain", "no install
  snapshot" and "the builder refuses a dirty tree by design" as *not run with a reason* instead of
  as failures - each one measured, not guessed.

## Design guidance for the R05 API wiring (learned the hard way)

To make FSRS the real default, `record_review_keyed` must take the interval as a
parameter (`Option<i64>`, `None` = scheduler unavailable) instead of computing the
ladder internally. Do it by **parametrizing the existing keyed path** — an enum
(e.g. `Ladder` vs `Explicit(Option<i64>)`) plus one private helper that both
public entry points call — rather than by copying the dedup/insert logic into a
second function: two copies of the event-key dedup rules will drift, and the
duplicate-key/conflict semantics are exactly what R2 EVENT-01 pinned down. Keep
the observable contract explicit: a replayed retry returns the original receipt
(`-1`), an unavailable scheduler records the event with `next_review` NULL, an
explicit `schedule: unavailable` marker and its own sentinel (`-2`), and the
conflict/missing-key errors stay unchanged.

Attempted-and-reverted (no code landed) while doing this with a tight budget: an
insertion that left a duplicated legacy body in `learning.rs`. The tree was
reverted to the verified `469f54a` state instead of committing a half-refactor;
prefer editing the file with the edit tool over scripted line surgery.

## Update — round 89 (R15/F05: the reading order is modelled, and reported)

The matrix had recorded one plain sentence for text PDFs: *there is no reading-order or
column-layout model*, so a two-column page was projected in whatever order the engine
returned. It now has one.

### What the worker does now

The projection's reading order is decided by the worker and **reported as a fact with its
reason**, once per page:

- the model is **one vertical gutter with text on both sides, then column by column and top
  to bottom**;
- it **may only reorder**. If the reconstruction would change *which lines the page holds*,
  the model refuses itself, keeps the engine order and records why;
- it **stands down entirely** when the engine text carries blank separator lines, because a
  line-level reconstruction would not carry those;
- a **single-column page comes back exactly as the engine gave it**, so the model costs
  nothing where there is no layout to model.

### The measurement that changed the design

The first version ordered **blocks**. It would never have applied to a real two-column page,
and the reason is measurable: on an 800x600 page with six runs inserted left, right, left,
right, the engine returns **three blocks that each span both columns** — so block-level
ordering cannot see the columns at all. The **lines inside** those blocks carry the real
per-column boxes. The model was rewritten at line granularity because of that measurement,
not because of a guess.

## Update — round 91 (R15/F04: the OCR reading order, and why it needed a split)

Round 89 fixed the reading order for **text PDFs**. The same gap was recorded for images —
*reading order exists only as line order* — and it turned out to need a different shape of
answer.

### What the gap actually was

The `image.ocr` route runs Tesseract in **single-block mode** (`--psm 6`). Measured on a
two-column sample, the engine returns

```
LEFT FIRST RIGHT FIRST
LEFT SECOND RIGHT SECOND
LEFT THIRD RIGHT THIRD
```

so a *visual* row of two columns comes back as **one line**. The missing piece was therefore
not a sort but a **split**: the model cuts each engine line along a vertical gutter that no
word box crosses, then reads column by column, and the review-region list follows the same
order. The invariant is consequently the **word multiset**, not the line set — splitting a line
is exactly what the engine's single-block layout got wrong, but no word may be added or lost —
and the engine order is kept whenever the reconstruction would not account for exactly the same
words.

### Three measurements, three corrections

1. **Measure the engine before designing.** The interleaving above was observable, so the
   model had a real job; on a single-column sample the model stands down and the text is
   byte-identical to the engine's.
2. **Do not trust the engine's line ids for rows.** Grouping a row's words by their TSV
   `line_num` turned `LEFT SECOND` into `SECOND LEFT`, because words printed on one visual row
   came back under different line ids. Rows are now grouped by overlapping vertical extent.
3. **One pixel must not reorder a row.** Sorting a row by `(y, x)` let a one-pixel baseline
   difference flip two words of the same row. A row is now ordered by `x` alone.

### Receipts

`tests/test_worker_ocr_reading_order.py`: **9 passed** — the two-column sample now reads column
by column, and the same file **asserts what the engine produced for that image**, so the premise
cannot rot; the single-column sample is unchanged; the review regions follow the reading order;
anchors still match the projected text; the guard is shown refusing a reconstruction that would
not account for the same words; the one-pixel baseline case; and the too-few-words case.
Existing OCR tests 23 passed / 4 skipped; `archeaxis-application` 19 groups / 71 passed / 0 failed.

### F04 is still partial, and the record now says exactly why

The model fixes **column interleaving and nothing else**: a phrase the engine misread stays

### The one gate a fresh checkout cannot pass, and why that is correct

`check_taskpack_integrity.py` attributes the two live progress files against the **install
snapshot** in `.project-local/runs/taskpack-0910-shipped/` — an **ignored receipt**. Without it
the checker refuses to attribute the divergence instead of assuming the best, which is the right
behaviour and is now recorded rather than glossed over.

Two things were measured rather than assumed, because the obvious repair (reconstruct the
snapshot from tracked data) does not work:

1. The snapshot is a **small template** — `EXECUTION.md` 140 bytes, `STATE.json` 971 bytes — and
   it was **replaced** when the executor began recording progress, not appended to:
   `sha256(live[:installed_bytes])` does not equal the manifest digest, and the live files do not
   start with the snapshot.
2. That template appears **nowhere in either file's git history**, so attribution cannot be
   rebuilt from tracked data alone.

The claim in the record is therefore narrower and exact: every slice cites at least one tracked
pointer a fresh checkout can re-check, and **this one gate additionally needs the install
snapshot that no fresh checkout has**. STATE (under R00, whose evidence includes that gate) and
the evidence index's R00 row both say so now.

### Method note worth keeping

A gate that is green in my working tree is not the same thing as a gate that runs in someone
else's checkout; here the two differed by exactly one ignored receipt, and the difference had
only ever been asserted in prose.

## Update — round 94 (R15/F15: a folder, ingested resumably)

The archive route reads **one container**. Nothing read a **directory**, and F15 recorded that
as a gap. `scripts/ingest/directory_batch.py` now walks a folder, imports each file as its own
source through the Core's HTTP API, enqueues the job the file's kind calls for, and appends one
JSONL line per attempt — the manifest **is** the resume state.

### The rules it will not bend

- **The latest attempt that actually did something decides**, the same rule the legacy
  processing ledger records, so a later failure is never hidden by an earlier success.
- **Every exclusion is reported** — excluded directories, hidden files, the limit — instead of a
  path disappearing quietly.
- **It never guesses a kind.** A file it maps to no kind is imported and recorded as carrying no
  job, with the reason.

### Measured against a real Core

A five-file folder (markdown, HTML, a real PDF, a nested text file, and a file with an extension
nobody can name): run 1 enqueued 4 jobs in 9 Core calls; **run 2 made zero Core calls** with 5
skips; after one file changed, run 3 made exactly 2 calls and re-processed only that file. The
`.git` directory was excluded and the exclusion appeared in the receipt. The manifest held 15
lines for three runs of five files. `tests/test_directory_batch.py`: 16 passed, including two
guards that check the driver's extension table against the Core's own media-type table and route
kinds so the driver cannot invent either.

### Two things running it taught that reading would not

1. **A real Core accepts the import of a file whose extension it cannot name.** The media-type
   refusal happens when a route is resolved *for a job*, not at import. So the driver imports
   such a file, records that it carries no job, and names why — guessing a route would either
   fail or hand content to a reader that cannot open it.
2. **A third run exposed a defect in the resume logic.** The second run's `skipped_unchanged`
   line overwrote the "job already enqueued for this content" fact, so the third run redid the
   entire folder. The decision now reads the latest attempt that *did* something, and a test
   pins it (`test_a_third_run_still_skips`).

### F15 is still partial, and the record says why

The driver is a **script that speaks HTTP**, not a Core route or a UI affordance, so a folder is
ingested by running it rather than by asking the product; the member relation is still an origin
reference rather than a first-class container-to-file edge; members beyond the extraction caps
are not expanded; and a member that has been read is still not promoted to knowledge. The matrix
still reads 0 complete / 14 partial / 2 custody-only.
