# AAOS 六项核心能力：本次对话完整汇总与开发交接文档

**主题：** 豆包分析审计｜核心优势判定｜六项能力纠偏｜产品架构｜实施路线｜验收标准  
**归属：** AAOS / ArcheAxis Knowledge / 星环知识平台  
**版本：** 对话整理 V1.0 · 2026-10-10  
**性质：** 对话成果与增量开发建议；**不是新的项目权威文件、发布证明或已经执行的任务回执**

> **最终共识：** AAOS 的双向掌握度、BKT、时序图谱、分层记忆、经验蒸馏与技能演化**存在真实代码及设计基础**；豆包报告的问题主要是把“已实现某个模块”扩大为“已形成成熟产品能力”，把“值得验证的系统组合”写成“全球独有”。六项能力**可以作为核心能力主线**继续完善，但真正的产品优势必须由真实使用、受控验证、版本与效果对照来证明。

## 第一部分｜本次对话的结论与决议

### 1. 本次对话依次解决了哪些问题

本次对话围绕以下四个连续问题展开：

1. **豆包的报告是否可信？** 审核其“人机双向学习操作系统”的定位、六项算法、竞品横评、演示方案以及是否存在夸大。
2. **既然确有代码，是否意味着方向正确？** 明确“有实现基础”“设计值得保留”“算法和规则需要修正”“效果仍需验证”四个不同结论。
3. **六项是否构成 AAOS 的核心优势？** 明确它们可以成为**核心能力**，但不能仅凭文件、算法名称、演示图或自身评分断言已拥有竞争优势。
4. **具体怎么开发？** 确定以一个 Rust Core 权威写入链路承接六项逻辑能力，先做双向最小闭环，再联动时序、记忆、经验与技能的长期复测，并设置负向验收用例。

本文将“已看到的代码事实”“对设计的判断”“推荐修正”“应由本地 Agent 再验证的事项”分别表达。正文汇总各轮讨论，第二部分完整保留此前产出的六引擎开发蓝图与 48 项首轮测试用例。

### 2. 最终判断：属于什么层级的核心优势

**结论 A｜核心能力：是。** 六项机制能够支撑 AAOS 的长期差异化路线：同一知识既服务人的学习，也服务机器的知识调用与可验证复用，并随证据、经验和任务结果迭代。

**结论 B｜原创算法：不宜整体称是。** BKT、FSRS、分层记忆、时间知识图谱、经验规则化及反馈改进各有成熟的研究或产品先例。AAOS 的创新更可能体现为**有边界的组合方式、数据与证据契约、双向用户流程和可靠性**，而不是所有组件由 AAOS 首创。

**结论 C｜已经成熟的竞争优势：尚未证实。** 需要在正式桌面端证明真实使用、机器调用、知识更新、异常恢复、跨版本一致性，以及对简单基线的增量收益。

**结论 D｜工程方向：保留并修正，不推翻重建。** 不能因存在明显问题就否定双向学习，也不能只在旧 Python 模块上增加代码而不确认其正式调用资格。

**价值主张建议：** “**同一份可信知识，人学得更深，AI 用得更准。**” 可继续沿用，但须作为产品愿景与价值主张；对外“已支持”必须按实际测试与安装态证据描述。

### 3. 豆包总结：哪些应保留，哪些必须改写

| 豆包主张 | 审核判断 | 本次采用的表达或处理方式 |
|---|---|---|
| AAOS 不只是笔记工具 | **基本认可** | 改成“不止是笔记工具”；保存、编辑、阅读仍然是第一层用户体验。 |
| 六项核心算法，竞品几乎都没有 | **明显夸大** | 改成“六类重要能力机制”；分别标注代码、接线、验证及效果层级。 |

| BKT 带 EM/隐马尔可夫算法 | **源码有依据** | 仍需数值测试、参数校准、接入正式学习事件，不能等同于真实学习收益已证明。 |
| 时序图谱能还原任意历史事实 | **目标合理，现有实现仍有历史查询风险** | 区分现实有效时间和系统获知时间，并测试被替代版本历史查询。 |

| 三案例／80% 一致即可生成专家规则 | **有程序阈值，但验证不足** | 将阈值视为进入下一步审查的门槛，新增案例独立性、反例和留出任务。 |
| 技能补丁全测试通过、回归不超过 5% 即可演化 | **部分源码支持，但表述过度完整** | 必测指标不能缺失；区分评估、注册、启用、观察与回滚。 |
| 每个 AI 回答必须有 EvidenceAnchor，否则拒绝 | **与正式普通内容保存原则冲突** | 仅对特定专业可信提升／执行用途严格限制；草稿、灵感、假设可先保存。 |
| “全球独一份”“竞品都做不到” | **无充分证据** | 删除全球唯一论断，采用可复现实测比较。 |
| 做 30 秒 M3/K6 对比演示 | **展示直观，但容易误导** | 改为“可解释的人的能力、机器资格、证据状态、下一行动”真实案例演示。 |

**竞品横评特别更正：** 原表把 Obsidian、Notion、Logseq、RemNote、Anytype 等产品简化为一组“✗”，忽略了插件生态、功能更新与不同系统边界，不能作为权威比较。尤其不能说 Anki／RemNote “只有简单间隔重复”；两者均支持 FSRS。BKT、分层记忆、时间图谱和可复用技能在 pyBKT、MemGPT、Graphiti、Voyager 等项目中均存在相关先例。差异化需比较**完整使用旅程**，不是只比术语。

**补充核查：** `app/knowledge/co_learning_loop.py` 确有双向行动分派逻辑；但分派“需要蒸馏”不等于本次调用已自动完成蒸馏，教学计划也依赖提供实际教学材料。正式 Rust 路径的 `crates/archeaxis-api/src/runtime/colearning.rs` 已包含机器回答、对应纠正候选与记录路径的代码，仍须验证它与六模块及桌面 UI 的实际贯通情况。

#### 4.1 不可忽略的反例

- **K1 不等于能教人：** 机器仅完成索引时，不可单凭 K 数字大于 M 就获得教学资格。
- **M7 不等于说过一次讲解：** 一条 `teaching_evidence=True` 的标记不足以说明形成稳定专家能力。
- **BKT 概率不是专家评分：** 后验掌握概率与技能等级、迁移能力、事实真实性分属不同维度。
- **当前被替代，不等于历史无效：** 旧事实今天不活跃，不意味着用户查询过去时不能看到它。
- **有 tag 不代表授权：** 任意普通标签或“我喜欢”句子不能静默进入 L4 长期偏好。
- **三条案例不保证独立：** 重复记录或模型虚构案例不能作为三份真实证据。
- **测试字段存在不代表测试执行：** 缺少必须基准、错误指标方向或未发布读回时不得给出“升级成功”。
- **有证据锚点不保证真实：** 原件锚点、识别忠实度、观点支持、使用资格与人体学习效果必须分开。

### 5. 从“六项能力”到“实际核心优势”的判断标准

只有当至少三个维度有证据时，才适合将目标从“核心能力”升级为“已证明的竞争优势”：

**用户结果：** 相同时间、相似任务下，延迟回忆、迁移使用或真实作品／问题解决表现相较简单基线有所改善。

**机器结果：** 固定模型、工具、任务与预算，增加获准知识、记忆、经验规则和技能演化之后，真正减少重复错误并提高可用质量，不只增加流程复杂度。

**可靠性结果：** 时间版本可查询、授权作用域不泄漏、错误引用可纠正、任务失败可恢复、技能升级可拒绝或回滚。

**不把内部指标当成果：** `M3→M4`、`K5→K6`、记忆条数或生成技能数量只是中间状态。必须测量用户实际收益与可复现效果。

### 6. 产品定位、证据治理与三项目边界

#### 6.1 建议保留的定位

**对外简版：** “同一份可信知识，人学得更深，AI 用得更准。”

**说明版：** AAOS 是本地优先的人机双向学习与可信知识工作台：能够先保存、阅读、编辑和组织内容，再根据内容与用途连接学习练习、知识依据、AI 资产和实际反馈。

“学习操作系统”可用于远景描述，**不意味着**通用操作系统、通用 Agent Runtime、工作流总调度平台，也不要求实现新的基础模型训练平台。

#### 6.2 必须分清的判断维度

- 内容允许保存，不等于其主张已经核验；没有专业外部证据也不妨碍记录灵感或探索假设。
- OCR／ASR 识别与原件一致，不等于原件中的观点正确。
- 有引用锚点，不等于引用真正支持该结论；引用支持也不意味着任意场景适用。
- 内容被采用，不等于人会了；人会了，不等于 AI 技能可靠可执行。
- AI 能调用技能，不等于通过验证；任务通过一次，不等于长期稳定或可跨模型迁移。
- 某项功能在旧 Python 模块或历史演示中存在，不等于当前正式桌面端已通过安装态验收。

**证据 fail-closed 的适用方式：** 将严格阻断用于需要严格依据的专业结论提升、受控执行或高风险权限；普通笔记、个人假设、草稿与待核验内容应允许保存。探索性 AI 响应需诚实标记不确定性，不能伪装成已核验结论。

#### 6.3 三项目协作边界（延续现行已整理任务包）

| 项目 | 主要责任 | 在六项能力里的位置 |
|---|---|---|
| **AAOS** | 知识正文、来源、版本、学习状态、AI 知识资产资格 | 六项知识与学习机制的权威归属；长期证据与候选处理。 |
| **DESIGN-LAB** | 专业设计判断、设计能力包、视觉表达、课件／动画制作、原生设计产物 | 从 AAOS 读取获准知识，制作图解、视觉教学、练习素材，回传表达与学习相关候选反馈。 |
| **WORK-LAB** | 工作流、编程实践、执行环境、技术复现、AI 治理实践 | 贡献真实使用回执、失败经验、复测环境与技术候选；不替代 AAOS 知识单写者。 |

三个仓库**不合仓、不共享业务数据库**；通过版本化、带来源与权限的受控交换连接。相同人或同一模型多次自评，不能声称形成独立三方审计。跨项目知识纠正须经过相应责任方和授权，不暗中覆盖原始记录。

#### 6.4 与此前任务包的关系

本次会话属于 **2026-10-09 AAOS 综合任务包与 UI 任务包的增量补充**：深化双向掌握、BKT、时序知识、记忆、蒸馏、技能演化的技术与验收定义，而不是替代原有 CAP 编号、正式 AAOS-01 活动队列、系统母定义或另建第七套权威文件。实际有效条款应被本地执行器映射入现有相应规范、台账、能力目录和测试。

现行技术方向为 **React／TypeScript／Vite + Tauri 2 + Rust Core 单一业务写入者 + SQLite/CAS + 隔离 Python workers**。正式写入和版本控制走 Core；worker 完成计算、模型调用或候选生成，不直接写权威业务库。知识图谱、全文/向量与记忆索引是可重建投影；不需要六套微服务。

### 7. 推荐的真实演示：不再讲“AI 比你高三级”

原豆包的“30 秒 M3/K6，给你三道题”有记忆点，但**等级不同量纲，学习效果未经验证**。建议用一个可复现的知识节点演示真实流程，例如“视觉层级”“版式主次”或“某个开发环境常见错误”。

**演示 A：人类学习。** 显示“已经能够解释、陌生应用还未测试”；提供一项对应练习；记录真实答题、提示使用及反馈；解释能力状态变化来源。

**演示 B：人教系统。** 展示一次 AI 的不理想结果及用户修改；生成附有条件和反例的经验候选；在新的任务中验证，形成有限用途技能，而不是自动宣布“AI 学会专家经验”。

**演示 C：知识变化。** 更新一个来源版本，仍可查历史状态；提示受影响课程和技能；保留历史学习记录，并让必要的机器能力进入复测状态。

**三项目联合演示（非首轮强依赖）：** AAOS 管理知识与学习目标；DESIGN-LAB 产出图解、动画或课件；WORK-LAB 贡献真实环境执行与技术纠错；回传的反馈由各自责任方判断并提请修订。展示真实交换回执，而非只录 UI 跳转视频。

### 8. 开发优先级：先闭环，不把六项重写成六个独立后台

| 建议阶段 | 主要事项 | 完成声明需要什么 |
|---|---|---|
| **0｜现场和依赖对账** | 核对本地 HEAD／dirty／worktree；分辨正式调用、可复用算法、历史模块、已被替代代码。 | 有明确的调用链与代码／数据／测试证据。 |
| **1｜写回基础** | 复用 ID、版本、事件、授权、幂等、冲突及恢复契约；缺什么补什么。 | 普通内容可保存，重试不双写，重启能读回。 |
| **2｜人的最小闭环** | 真实学习观察→BKT／能力状态→下一行动建议→UI 读回。 | 每个建议可解释，未测不冒充已掌握。 |
| **3｜机器的最小闭环** | 真实纠错→经验候选→范围验证→技能提案→调用／回滚。 | 真实独立任务证明有用，未测不激活。 |
| **4｜六项联动** | 双时间知识、记忆许可、来源变化影响课程／技能、失效复测。 | 历史查询正确，权限与修订不漂移。 |
| **5｜产品和收益验证** | 正式桌面、安装态、备份恢复、长期对照试验。 | 工程正确与学习／机器增益分别报告。 |

阶段 2 与 3 必须相邻推进，防止 AAOS 退化为“只有复习”或“只有 AI 技能管理”。每阶段**先复用合格现有组件**，不得只因为名称不匹配就重建。

### 9. 本次对话统一确立的禁止误判与实施红线

1. 不以“有代码、测试文件、22 张页面效果图、CI 数量”替代正式桌面使用与安装态验收。
2. 不用 M/K 数字直接比较人和 AI 的智慧、知识真实性或专业水平；M 等级、K 资产成熟度、机器任务能力凭证、证据状态必须分开。
3. 不把 BKT 后验、FSRS 复习概率、Teach-back 评分加为一个统一的“掌握准确率”。
4. 不让时序图谱投影成为第二权威数据库；不把今天的状态套回历史任意时点。
5. 不让重复案例、模型虚构案例或自评形成独立证据；保留反例与来源共同谱系。
6. 不允许工作流或模型私自提升 L4 长期偏好、改变用户权限或跨项目复制私有内容。
7. 不把技能 `approved`、`patch applied` 或仓库里存在新文件等同于真实注册、启用、复测与回滚成功。
8. 不把“不通过严格证据门槛”扩大为“不允许普通内容保存”。
9. 不直接改 WORK-LAB、DESIGN-LAB 私有数据库；外部交换是版本化、获准、可撤回的最小材料。

### 2. 不改变的工程边界

沿用现有 React/TypeScript/Tauri → 有限宿主接口 → Rust Core → SQLite/CAS 的正式路径。Python workers 只计算或生成候选，不直接写权威数据库。项目合同已经禁止 UI、worker、agent 直接 SQL 和双写。[R1]

普通保存不等待外部证据、云端服务或人工审核。来源核验、专业支持分析、内容采用、学习测量和执行许可分别记录。严格限制针对相应的可信提升或高风险执行，不针对一切草稿和探索。

不因本蓝图新增六个微服务、六套数据库、第二个知识主库、完整事件溯源平台或图数据库。现行合同明确将图数据库和 full event sourcing 等列为阶段外事项。[R1]

三项目独立仓库、独立业务数据库。AAOS 管本系统知识、学习状态与资产资格；WORK-LAB 负责其执行、技术复现和客户端适配；DESIGN-LAB 负责专业设计判断、表达与教学材料制作。跨项目通过已获准的版本化接口交换最小必要材料，不直接读写彼此数据库，不把 AAOS 六引擎建设变成强制接管另外两项目的运行时。

### 3. 先统一对象、版本和可追溯写回

以下是逻辑对象，必须优先映射已有 schema，而不是按名称机械新建表。

- `unknown / not_assessed / insufficient_data / failed / not_applicable` 分开，不能全部转换为零分。

这些要求不等于引入“全系统事件溯源”。允许在现有表上采用事务、版本记录与可重建投影。

### 4. 引擎一：双向掌握度与行动建议

#### 4.1 目标

回答“这个人在当前任务上会什么”“当前系统配置能可靠做什么”“知识依据有何限制”“下一步有哪些合适动作”，而不是判断人和 AI 谁的等级数字更大。

现有 `app/knowledge/dual_mastery.py` 直接比较 M/K 索引；`bkt_mastery` 字段没有参与人类等级函数。应保留接口兼容信息，修正决策语义，不把旧数字差值继续传播到正式 UI。[R2]

#### 4.2 第一版实现

人的状态采用任务维度：回忆、解释、解决、迁移、创造、教学。每项记录未测、初步表现、重复验证、待复测等语义，并引用真实任务结果。M0–M7 可以保留为可解释的摘要，不作为唯一真相，也不能把一次“讲解成功”自动等同于专家。

机器侧拆成两部分：K0–K8 表达知识资产的加工/复用成熟度；MachineCompetenceReceipt 表达某个执行配置在指定任务上的实测能力。收到文件、建立索引或创建技能，均不等于获得教学或执行资格。

机器能力至少绑定：知识版本、技能版本、模型/提示词/工具配置指纹、任务范围、测试集版本、评估时间。更换模型后允许复用资产，但不无条件继承旧验证结论。

证据侧底层至少分开：核验状态、时间适用性、争议状态、采用/使用范围。UI 可以显示摘要，但不能因为内容“较新”就抹去争议。

建议输出是有顺序的行动列表，而不是必须五选一的互斥动作：教学、能力测量、经验提炼、协作、材料补充、证据复核都可以带理由返回。普通保存与探索不进入严格证据阻塞流程。

逻辑接口示意，非已存在的命令名称：

```text
assess_human(observations, rubric_version) -> human_state
assess_machine(receipts, task, execution_profile) -> machine_state
recommend_actions(goal, human_state, machine_state, evidence, policy)
  -> [{action, reason, evidence_refs, scope, limitations, consent_required}]
```

### 5. 引擎二：BKT、复习与任务测量

#### 5.1 目标

BKT 用来估计某个可定义技能的潜在掌握状态、预测后续回答。它不是专家分数，不等于记忆调度，也不自动证明迁移与创造能力。pyBKT 提供模型拟合、预测和验证的现成参考。[R4]

#### 5.2 数据先于训练

先定义少量可评估的知识技能与题目映射。一个回答可能涉及多个能力，但第一版应优先采用主技能清晰的任务，避免把一题总分重复当作多个独立知识点的正确证据。

观察至少包含：学习者、知识版本、题目/任务版本、原回答、正确性或分项评分、提示使用、评分器、发生时间、会话/尝试标识。创作、美感和复杂设计表现优先用分项评估标准，不能硬塞进二值 BKT。

参数表示：`L0` 初始概率、`T` 学习转移概率、`G` 未掌握时猜对概率、`S` 掌握时答错概率。对于答对：

```text
posterior_after_answer = p*(1-S) / [p*(1-S) + (1-p)*G]
next_prior = posterior_after_answer + (1-posterior_after_answer)*T
```

答错时使用相应的错误似然。记录“观察后的后验”和“学习转移后的下一步先验”的不同语义；现有 update 的返回值包含转移，不要把名字误当成严格的观察后验。[R3]

#### 5.3 分阶段实现

第一版保留当前纯计算实现，建立手算/参考实现对照和边界测试，以版本化默认参数运行。没有足够观察时显示“基于默认先验，尚未校准”，不捏造个人训练结论。

第二版才做 EM 拟合。按学习者、技能和时间保存序列，不能把不同人的答题随意拼接。个人数据不足时先使用共享或领域先验；个性化不是强行给每个知识点拟合四个不稳定参数。参数优化在后台作业中执行，而不是每回答一次都训练。

评估以时间外推或学习者分组的留出数据进行；同时比较默认 BKT、拟合 BKT和简单历史正确率基线。报告 Log Loss、Brier score/校准和样本量；不能只报训练集正确率。小样本不足以定论时维持旧参数。

BKT 与 FSRS 共用原始观察，但输出分开：BKT 辅助技能状态推断；FSRS 输出复习时机和回忆概率。复述、迁移、创造采用任务证据。不得相加 BKT 与 FSRS 的概率，或把同一次回答重复计算为两次独立能力证据。FSRS 优先复用项目已吸收、锁定版本的实现。[R5]

| ID | 必须覆盖的情况 | 期望 |
|---|---|---|
| BKT-01 | 手算答对/答错序列 | 与参考公式在约定数值容差内一致 |
| BKT-02 | 同一回答重试上传 | 只更新一次 |
| BKT-03 | 缺失答案、取消或无法判分 | 不当作答错 |
| BKT-04 | 使用提示后答对 | 保留提示条件，不冒充独立作答 |
| BKT-05 | NaN、无穷、越界参数、退化观测 | 明确拒绝/标记异常，不输出伪概率 |
| BKT-06 | 只有少量个人数据 | 不强制宣称个性化训练有效 |
| BKT-07 | 断开云端并重启 | 已有记录与本地调度可恢复 |

### 6. 引擎三：时序知识图谱

#### 6.1 目标与存储

在既有知识版本、来源和 SQLite 关系上建立可重建的图谱投影；不是建立第二个知识数据库。Graphiti 的时间语义可作为参考，不意味着必须整体引入其服务和存储依赖。[R6]

底层区分：实体、声明、来源版本、证据关系、声明适用范围和版本修订。声明不是无条件事实；来源更新也不自动使旧声明错误。

#### 6.2 双时间

需要分别表示现实适用时间与系统已知时间。逻辑字段可为：

```text
valid_from / valid_to       现实适用区间
recorded_from / recorded_to 系统记录这一版本断言的区间
```

查询接受 `valid_at` 与 `known_at`。采用半开区间并统一 UTC 解析。空的起止时间明确表示未知或无界，不能混淆。

例：某规则 3 月 1 日生效，系统 3 月 10 日才录入。回看“3 月 5 日实际适用什么”和“截至 3 月 5 日系统知道什么”是两种问题。后录入的信息不能泄漏到更早的“当时已知”查询里。

旧记录今天被替代，不代表它在过去的适用时点应被过滤掉。新版本也不能无条件继承旧版本的有效起始时间。更正历史断言时保留前一系统记录版本，不能只覆盖一行而丢失 known-at 语义。

#### 6.3 冲突与影响

先按实体、谓词、作用域、条件和重叠时间筛选候选关系，再做规则或语义比较。AI 可以提出冲突候选，但不能把“新内容出现”直接等同于“旧内容已失效”。专业声明的替代依据和采用策略必须可追溯。

来源或规则更新后，计算受影响的引用、学习材料和技能。对机器标记相关资格待复测；对人提示更新差异和相关复习，不删除已经发生的学习记录，也不推断人瞬间失去全部能力。

#### 6.4 首轮验收用例

| ID | 必须覆盖的情况 | 期望 |
|---|---|---|
| TIME-01 | 今天已 superseded 的旧版本 | 历史有效时点仍可正确查询 |
| TIME-02 | 信息晚于实际生效时间录入 | valid-at 与 known-at 给出正确差异 |
| TIME-03 | 相同主体、不同使用范围的声明 | 不误判为直接矛盾 |
| TIME-04 | 声明存在真正重叠冲突 | 两边来源与条件均保留 |
| TIME-05 | 仅文档编辑时间变新 | 不自动提高内容可信度 |
| TIME-06 | 来源更新使某规则待复核 | 能定位受影响技能与教学材料 |
| TIME-07 | 时区、边界时刻与空时间 | 结果符合约定的区间语义 |
| TIME-08 | 重新构建图谱投影 | 不丢原件、版本或引用身份 |

### 7. 引擎四：L1–L4 分层记忆

#### 7.1 目标

记忆是“哪些信息可以在当前任务中被调用”的机制，不是越多越好，也不是第二份权威知识。分层上下文管理可参考 MemGPT，但 AAOS 的分层策略与隐私授权须独立实现。[R7]

| 层 | 建议语义 | 初期实现 |
|---|---|---|
| L1 | 当前任务上下文 | 受 token/容量限制的活动窗口，必要信息可固定 |
| L2 | 项目作用域上下文 | 引用项目材料与获准回执，不跨仓直读业务数据库 |
| L3 | 可复用领域知识 | 从获准知识与技能生成的可重建投影 |
| L4 | 用户明确认可的偏好/习惯 | 带目的、作用域、授权、撤销记录 |

#### 7.2 检索与写入

检索先做身份、作用域、授权与用途过滤，再排序；不得让高相关性得分覆盖硬权限。严格用途与探索用途使用不同的资格策略，未验证内容可以在获准探索中被明显标记地使用。

先建立全文检索基线，再根据实测决定是否增加向量召回与重排序。记忆结果应返回原始引用、版本、进入上下文的原因和使用限制，而不只是摘要。

L1 的“50 条”只能是可调的工程参数。活动窗口淘汰不等于删除原始材料；长文本应结合 token 预算处理。向 L3/L4 提升必须有相应采用或授权依据，不能因为提及次数多就自动成为专业规则或长期人格。

L4 需要明确的偏好授权标识及真实授权记录，任意非空 tag 不够。引述他人说“我喜欢……”也不能变成用户偏好。用户撤销时，停止召回并处理索引、摘要和派生缓存；日志保留与原件删除按既有策略区分，不借 append-only 忽略撤销。

检索材料中的“指令”按内容处理，不能自行更改系统权限或启动执行。

#### 7.3 首轮验收用例

| ID | 必须覆盖的情况 | 期望 |
|---|---|---|
| MEM-01 | 项目 A 请求项目 B 私有内容 | 在召回和模型输入前阻断 |
| MEM-02 | 普通 tag + “我喜欢” | 不自动获得 L4 授权 |
| MEM-03 | 引用他人的偏好 | 不记成用户本人偏好 |
| MEM-04 | 撤销某条偏好 | 后续召回及派生缓存不继续使用 |
| MEM-05 | L1 超容量 | 活动窗口缩减，但原内容不丢失 |
| MEM-06 | 多次重复同一经验 | 不自动成为 L3 已验证规则 |
| MEM-07 | 过时来源、严格任务 | 依用途策略处理并显示限制 |
| MEM-08 | 记忆文本含恶意执行指令 | 不提升权限、不触发工具执行 |

### 8. 引擎五：人类经验蒸馏

#### 8.1 目标

把人的判断转为有条件、有反例、可测试的经验资产。这里的“蒸馏”首先是知识表达与验证，不是神经网络知识蒸馏或基础模型微调。

输入优先来自真实任务中的纠错：原输出、用户修改、修改理由、任务背景、前后结果和不适用条件。普通笔记与单个案例可以保存为候选，不能因为尚未构成规则就拒绝接收。

#### 8.2 候选结构

```text
principle_id
statement
applicable_when
recommended_action
exceptions
supporting_case_refs
counterexample_refs
source_and_owner
allowed_uses
evaluation_status
revision
```

AI 可以抽取候选、追问遗漏条件、组织正反案例，但不能把个人风格喜好自动宣称为普遍设计规律，也不能把生成的虚构案例登记成真实独立证据。

现有“三案例、80%一致”最多先作为进入进一步审核的默认条件，不作为普遍可靠性的证明。按真实任务、来源、素材或情境聚类，避免把同一案例的多个描述计算成独立支持。记录反例而非删去反例提高比例。

建议流程：候选原则 → 补充条件与反例 → 独立案例核查 → 保留案例测试 → 限定范围试用 → 形成规则/技能提案。具体状态名映射现有 schema，不另造第二套权威状态机。

生成技能提案时明确输入输出、允许与禁止任务、依赖、权限、来源及适用范围。教学材料与可执行技能分别出包；二者都不自动激活。

#### 8.3 首轮验收用例

| ID | 必须覆盖的情况 | 期望 |
|---|---|---|
| DIST-01 | 单个真实案例 | 可保存，但不宣称已验证规律 |
| DIST-02 | 同一案例复制三次 | 不计为三个独立支持 |
| DIST-03 | 有明确反例 | 保留并调整条件/范围 |
| DIST-04 | 个人审美偏好 | 保持偏好身份，不自动成为事实 |
| DIST-05 | AI 生成的合成案例 | 标为合成，不冒充真实观测 |
| DIST-06 | 留出任务验证失败 | 不晋升相应使用范围 |
| DIST-07 | 原因说明被用户纠正 | 形成新版本，不覆盖原记录 |
| DIST-08 | 从规则生成技能 | 仍是待验证/待获准候选 |

### 9. 引擎六：技能演化

#### 9.1 目标

基于真实失败和效果改善技能资产，而不是允许 AI 无限制修改自身、系统约束或基准。Voyager 提供“可复用技能库 + 执行反馈改进、不必微调基础模型”的研究先例，但其结果不能直接作为 AAOS 的效果证明。[R8]

#### 9.2 首先记录可归因的使用结果

每次使用记录：任务及其版本、技能版本、模型/工具/环境配置、知识与记忆引用、输入输出、执行结果、质量测量、人工纠正、成本和耗时。明确哪些指标未测。

失败先区分知识过时、规则不完整、提示词问题、工具变化、网络/环境故障与评分不确定。网络失败不能直接作为“技能差”的证据；未完成执行也不能冒充质量评测失败或成功。

#### 9.3 修改与评估

初期一次补丁只解决清楚的问题。补丁生成在候选分支或候选资产中发生；不能直接写当前激活版本。测试集、评分规则、权限和判定阈值不允许由待评估技能自行改动。

评估分开发集、独立保留任务与不可退步的安全/边界案例。记录生成模型与评分器来源；同一模型自评不是独立实证。需要时用人工抽检或实际可执行检查补充。反复试错会消耗留出集的独立性，因此轮换保留材料、保留未见任务。

每项指标声明方向、单位、基准、容忍度及是否必需。不能对成功率、成本、耗时套同一个“5%”规则。必需指标缺失、NaN 或无法执行时，结论是未完成/不可判定，不是通过。成本或速度的改善不能掩盖安全或关键质量失败。

随机生成任务用成对的相同任务比较候选与基线，做必要重复并报告差异不确定性。低风险用途可以在用户预先批准的范围中自动化验证与试用；高风险启用保留人工批准。

#### 9.4 发布和回滚

完整链条：候选补丁 → 固定版本测试 → 评估回执 → 用途批准 → Core 原子注册新版本并切换有效指针 → 实际调用读回 → 监测 → 必要时切回旧版本。

版本切换校验被测载荷哈希、依赖与预期当前版本，防止测的是 A、用的是 B。重启后有效版本一致。回滚技能版本不自动撤销已经发生的外部副作用，外部执行需另有补偿或人工处理方案。

更换模型或软件后，资产可以迁移，但对应任务要做兼容复测；“可移植”不等于“跨模型效果完全一样”。

#### 9.5 首轮验收用例

| ID | 必须覆盖的情况 | 期望 |
|---|---|---|
| EVOL-01 | 未测任务/缺少必需指标 | 不返回已通过 |
| EVOL-02 | 成本下降但关键质量下降 | 按预定义策略拒绝或保留旧版本 |
| EVOL-03 | 候选试图修改基准或评分器 | 阻断并记录 |
| EVOL-04 | 测试后载荷发生变化 | 哈希不一致，不能启用 |
| EVOL-05 | 并发发布到同一技能 | 预期版本冲突不丢失更新 |
| EVOL-06 | 切换过程中故障并重启 | 活跃指针与注册状态保持一致 |
| EVOL-07 | 高风险技能自动请求启用 | 不越过所需批准 |
| EVOL-08 | 回滚并真实调用 | 使用旧版本，说明外部副作用边界 |

### 10. 开发顺序与阶段产物

这些是建议的增量切片；先映射当前任务，不创建另一份自称 current 的排期。

| 阶段 | 工作 | 通过条件 |
|---|---|---|
| 0 对账 | 当前权威、正式调用链、既有对象、旧模块位置、测试与开源吸收状态 | 每项有复用/修复/迁移/后置判断，不能仅按目录名判断完成 |
| 1 共用基础 | 版本、观察、回执、授权和受控写回的最小补齐 | 重试、并发、重启、恢复与普通保存均有实际测试 |
| 2 人类最小闭环 | 三轴任务状态 + BKT + 既有复习 + 基本证据引用 | 用户作答→更新→下一步建议→重启后续用 |
| 3 机器最小闭环 | 纠错→经验候选→独立验证→技能试用→新任务评估 | 新任务实测、引用可追溯、可拒绝与可回滚 |
| 4 六项联动 | 双时间、作用域记忆、更新影响、技能资格复测 | 来源变化能准确影响后续教学/使用，但不破坏历史记录 |
| 5 产品与效果 | 真实桌面入口、导出/恢复、对照试验 | 工程通过与收益证明分开报告 |

不把人的学习推迟到“先完成所有机器能力后”，也不把机器经验学习推迟到只有复习工具。阶段 2、3 是紧邻的双向最小闭环；第一轮可限定极少知识与任务，后续扩展覆盖面。

### 11. 统一 UI，而不是六个孤立后台

建议承接于四种工作界面：知识详情中的能力与依据区、学习工作区、经验与技能区、来源/版本时间线。记忆授权和“为什么召回此内容”用抽屉或设置承接，不强迫普通用户学习六套后台术语。

每个状态能打开原始依据；每个自动建议显示原因与限制；每个未完成任务显示可重试的真实状态。M/K 编码属于高级展开信息，普通界面优先表达“已能解释”“陌生场景待验证”“当前工具配置已通过哪些任务”。

### 12. 怎样证明它成为核心优势

工程正确性与业务效果分开评估。

人的收益：比较同等学习时间下的延迟回忆、陌生情境应用与真实作品/任务表现；不以系统自报的 M 等级上升作为唯一成功指标。单用户项目可先做匹配知识点、多轮小规模交替对照，不能由一轮展示外推长期效果。

机器收益：同一模型、同一工具、同一任务预算，比较基础检索、加获准记忆、加经验规则、加演化技能。报告成功率、重复错误率、依据使用错误、成本与耗时。逐项加入能力，检查复杂度是否产生真实增益。

可靠性收益：历史时点查询准确性、错误冲突率、失效知识误用率、权限泄漏测试、恢复成功与回滚完整性。测试集上的零泄漏是该测试集的结果，不是对所有未来场景的绝对保证。

如果某个新算法暂未胜过简单基线，保留结果和研究目标，在产品中继续用更稳妥的基线，而不是硬上线或删除长期能力定位。
