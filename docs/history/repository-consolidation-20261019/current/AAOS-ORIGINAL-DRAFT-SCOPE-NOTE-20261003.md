# 原创草稿持久化 · 范围说明（2026-10-03）

提出方 DSH。**本文不含实现；结论是「不在 M0 内做」。**

## 1. 现状（已核对源码，属实且标注诚实）

`原创` 侧栏那条 `持久草稿和版本历史 · 待接 Core` **不是假标签**：

- `MainWindow.axaml:285` 与 `:895` 两处 `保存草稿` 按钮 **`IsEnabled="False"`**，提示为 `保存到 Core 的功能尚未提供`；
- 界面文案明确写着 `草稿只保留在当前界面；保存到 Core 尚未提供，不会伪装成已保存来源。`；
- 快速捕获也标注 `草稿仅保留在当前窗口；尚未保存到 Core。`；
- **Core 侧完全没有草稿路由或存储**（全仓 grep `draft` 在 `crates/` 下只命中一条无关注释）。

按 F01 的标准（「必须说明不可提供的真实原因与所需动作」），**这一处已经合格**：它说清了为什么不可用，也没有把未保存伪装成已保存。

## 2. 所以这不是缺陷，而是一个未排期的能力

要实现它，最小可行的切面是：

| 需要 | 内容 |
| --- | --- |
| Core 存储 | 新增草稿表（草稿 id、类型、正文/链接、创建与更新时间、状态） |
| Core 路由 | `POST /api/v1/original/drafts` 保存、`GET /api/v1/original/drafts` 列出、`GET/DELETE .../:id` 读取与丢弃 |
| 契约 | 登记进生产 HTTP 契约（当前 45 对 → 增加），并声明 capability |
| 前端 | 启用两处 `保存草稿`、加载已有草稿、处理冲突与失败态 |
| 测试 | Core 契约测试 + 前端绑定契约 + 门禁 |

## 3. 为什么建议不在 M0 内做

1. **它是一个新能力**，不在 P0–P5 真实闭环（来源→转换→锚点→质量→审核→检索→课件→学习→纠正）的路径上。
2. M0 方向覆盖明确要求不得把额外能力「突然塞进当前闭环」；`docs/current/M0-DIRECTION-OVERRIDE-20260920.md` 全文**没有提到**原创编辑器，即无授权。
3. 它会新增**第二个写入面**。当前 vNext 的写入权威全部集中在既有几张表与路由上；新增草稿表要连带考虑备份/恢复、迁移、以及「草稿不是知识、不得被检索或当成来源」的边界。
4. 现状**没有对用户撒谎**，所以它不是「项目有问题」，只是「能力未提供」。

## 4. 若 Owner 决定要做：建议的最小切片

1. 只做**保存与读取**，不做协同/多端/冲突合并——单机单写者，冲突只有「窗口内容比库新」。
2. 草稿**不得**进入搜索、证据、知识或学习任何一张表；草稿只能被显式「提升」为来源（那个动作另议）。
3. 契约测试必须先钉住**「草稿存在也不能让知识/证据/搜索计数发生变化」**，再开放界面按钮。
4. 顺序：Core 表与路由 → 契约与声明 → Core 契约测试 → 前端启用 → 真机读回捕获。
