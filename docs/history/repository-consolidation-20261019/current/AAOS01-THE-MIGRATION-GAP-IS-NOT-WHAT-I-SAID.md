# AAOS-01：**迁移缺口的性质变了 —— 并更正我上一轮的读法**

## 1. 我原本的假设

第 116 轮我看到 `migrations: {applied: 6, pending: 4}`，提出的假设是：

> 「`migrate` 与 `status` 可能读的是**不同的数据库文件**。」

## 2. 实测：主库里的迁移记录**远多于 6**

我直接以只读方式打开运行时创建的 sqlite 文件，看 `schema_migrations`：

```
"schema_migrations": {"rows": …,
  "sample": [ … , "(16, 'axr_learning_truth_v2', …)",
                    "(17, 'axr_source_truth_v2', …)",
                    "(18, 'axr_distillation_review_v1', …)"]}
"table_count": 97
```

**主库的 `schema_migrations` 记录一路到 id **18**** ✓ —— 而迁移前备份里也各有 10 · 11 · 13 行 ✓

## 3. ⚠️ 所以我要更正第 115/116 轮的读法

我当时写：

> 「**迁移并未完成。**」

**那句话过宽了。** 更准确的是：

| 事实 | 表述 |
| --- | --- |
| 主库 `schema_migrations` 有**十余条**记录（到 id 18） | **迁移确实应用了大量内容** |
| `status` 路由报 `applied: 6, pending: 4` | **这是**另一个维度**的读数** |

**最可能的解释**：`status` 的那个计数是**按某个 owner 维度**统计的，
而**不是**整个库的迁移总数 ✓

**我的假设（两个不同的数据库文件）因此没有得到支持** —— **反而被这批证据弱化了**。

## 4. 我**不**声称的（这次的边界要划清）

| 不声称 | 原因 |
| --- | --- |
| 「`applied: 6` 就是某个 owner 的计数」 | **那是推断** —— 我**没有**读 `status` 的实现 |
| 「主库正好有 18 条」 | **我的输出被截断**，我只看到样本里最大的 id 是 18 |
| 「迁移全部完成」 | **同样因为截断** —— 我没看到总数 |

**本轮我能确定的只有两件事**：

1. **主库的 `schema_migrations` 记录数明显多于 6** ✓
2. **因此把 `applied: 6` 读成「全库只应用了 6 个」是错的** ✓

## 5. 下一轮（具体、低成本）

**直接数 `schema_migrations` 的行数并列出全部 id**（不做截断，写成文件再读），
然后**只读地看 `status` 里那个计数是怎么算出来的** —— 两者一对照，缺口就定性了。

## 6. 我的一个重复问题（第三次记）

**我的输出又被截断了**（只看到尾部），**所以我只能报样本、不能报总数**。
第 87 · 109 轮都犯过。**这次我明确：凡涉及计数，先写文件再读，不靠终端尾部。**
