# AAOS-01 Q13：**worker 亲见到了**

追了六轮（56→61）的那件事，本轮**看到了**：Core 真的派生了一个 `python.exe` 子进程。

## 1. 为什么这次能看到

第 59 轮查明：worker **不在 `machine.answer` 上**（那条路由 503「no worker is registered」）。
注册的能力是 **`text.extract`**。

而能力面那条路由**会做一次真实的 hello**（该测试文件的注释原话：*health observes a real hello*）——
**所以不必走完整导入管线，一次 GET 就够。**

## 2. 实测

```
"worker_seen": true
"worker_sightings": [{"pid": "22312", "name": "python.exe", "command": ""}]
```

| 事实 | 值 |
| --- | --- |
| Core PID | 17824 |
| **观察到的子进程** | **`python.exe`，PID 22312，父进程 = Core** |
| 能力查询 | **200** |
| **能力查询耗时** | **0.08 秒** |
| 监视线数 | 1（**只出现一次** —— 与「按调用派生」一致） |

**能力记录本身也点名了 provider**：

```json
"capability": "text.extract"
"default_provider": "...\\services\\python-workers\\transport\\text_ndjson.py"
"enabled": true
```

## 3. 我**必须**说清的局限

**那个子进程的命令行是空的**（`"command": ""`）。

所以我能确定的是：

| 我确定的 | 依据 |
| --- | --- |
| 它是 **Core 的子进程** | 按 `ParentProcessId = <core pid>` 过滤得到 |
| 它在**能力握手期间**出现 | 监视窗口与请求窗口重合 |
| 它是 `python.exe` | 进程名 |

| 我**没有**直接证明的 |
| --- | --- |
| **它的 argv 指向 `text_ndjson.py`** | 命令行取到的是空串 |

**间接证据很强**（能力记录里 `default_provider` 就写着那个脚本），**但那是记录的、不是我看它的命令行看到的。**
**我不把「记录说它是」写成「我见它是」。**

## 4. 于是 Q13 的三类记录都立起来了

| 类别 | 状态 |
| --- | --- |
| **进程树** | ✅ 三层链路（venv python → 探针 → Core），父子关系核对过 |
| **故障** | ✅ 四条精确记录（422 点名字段并列出该发的、400 未知类型、404 领域前置、503 缺能力） |
| **性能** | ✅ 就绪 **0.02 秒**、能力握手 **0.08 秒**、（被拒）0.01 秒 |

## 5. 方法上值得记一笔

**要看一个可能只活几十毫秒的进程，不能用「起一个 shell 采一次样」的办法** ——
本轮改成**一个长驻 shell 内部 60 毫秒轮询一次**，才在它存在的那一瞬间抓到它。
**我前两轮每次采样都要起一个 PowerShell 进程，注定抓不到。**
