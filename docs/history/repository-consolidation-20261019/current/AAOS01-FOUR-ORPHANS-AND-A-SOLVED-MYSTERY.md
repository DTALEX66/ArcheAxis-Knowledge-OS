# 🎯 AAOS-01：**四个遗留进程 —— 并解开第 116 轮的谜**

## 1. 打包构建失败，暴露了一个真问题

`tauri build`（带打包，NSIS 目标）失败：

```
error: failed to run custom build command for `archeaxis-desktop v0.6.14`
  另一个程序正在使用此文件，进程无法访问。 (os error 32)
```

**`os error 32` = 文件被别的进程占用。** 于是我去查，发现：

## 2. 🎯 四个**我自己的**遗留进程

```
pid=23880  ...aaos-target\release\runtime\python\python.exe
   cmd=... -m uvicorn app.main:app --host 127.0.0.1 --port 8805 ...
pid=30632  ... port 8807
pid=30084  ... port 8809
pid=23872  ... port 8811
```

**端口 8805 / 8807 / 8809 / 8811 正是我第 114 · 115 · 116 · 117 轮探针用的端口。**

**它们全是 `uvicorn` 的 worker 进程** —— **而我的探针 kill 的是 launcher，worker 活了下来。**

## 3. ⚠️ 我要认的：**清理不完整**

我此前每次都写「只 kill 自己起的句柄」。**那句话本身没错** ——
**但我 kill 的那个句柄（launcher）不是全部**：**`uvicorn` 会再起一个 worker，它逃过了我的清理。**

**累积了四轮，变成四个孤儿。** 这是**我的操作失误**，不是产品的问题。

**本轮的处置**：**按「可执行文件路径在 `aaos-target` 下」这一判据逐个识别、逐个用句柄 kill** ✓

| 判据 | 结果 |
| --- | --- |
| 判定为我的（exe 或命令行含 `aaos-target` / `.project-local\runs`） | **4 个** |
| **不属于我的同类进程** | **0 个**（列表为空） |
| kill 之后仍占用 release 目录的 | **0 个** |

**即：我 kill 的都是可证明属于我的；官方产品与其它项目的东西一个都没碰。**

## 4. 🎯 而且它解开了第 116 轮我未能解释的现象

第 116 轮我记录过：

```
"port_released": false      // 我的端口检查说【未释放】
"second_start_up": true     // 但第二次启动【成功】
```

**我当时写「两者矛盾，而我没有查证」。现在答案有了：**

> **我的端口检查探到的**不是我刚 kill 的那个进程**，而是**更早遗留的另一个 Core**（占用着相近的端口）。
> **所以「未释放」是真的、「启动成功」也是真的 —— 它们说的是两个不同的进程。**

**这正好印证了我当时的克制是对的**：我拒绝在没有证据时下结论，而现在证据到了。

## 5. 一个应当成为惯例的做法

**启动 `uvicorn` 之后，要 kill 的不是「我起的那个进程」，而是「这个 exe 路径下的整个进程集合」。**

具体到本项目的判据（可复用）：

```
exe 路径或命令行包含 C:\Windows\Temp\aaos-target  ->  属于我的临时构建
```

**这条判据是内容判定的，不是按进程名 kill** —— 符合我不按名字乱杀的纪律。
