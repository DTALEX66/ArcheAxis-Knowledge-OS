# 白话错误反馈与统一运行记录

Owner要求普通用户能看懂各环节出了什么问题、接下来怎么做，并能在一个地方查记录。范围包括正常页面的工程术语、操作失败反馈和集中记录；不修改用户导入的代码正文或专业资料，也不隐藏显式打开的技术详情。

## 已核实的问题

- `presentation/labels.ts` 已有 `failureMessage` 和 `userErrorMessage`，但部分消费页面直接显示 `Error.message`，混合中文与程序名、路径或错误片段仍可能进入普通提示。
- `DiagnosticCenter` 已由App挂载。原实现只在手动点击后收集最多50条当前工作区会话详情，不能称自动、持久或全覆盖日志。
- 原生实测学习队列仍显示ISO时间，属于显示收敛遗漏。合成测试正文里的代码、长编号和工程标记不当作产品静态文案缺陷。
- 未发现全局React错误边界或统一未处理异步异常兜底；不宣称已有崩溃恢复能力。

## 反馈规则

| 情况 | 呈现 | 内容与下一步 |
| --- | --- | --- |
| 输入缺项或格式不对 | 输入附近说明 | 指出需补哪项，保留输入，不反复弹窗 |
| 用户发起的操作失败 | 当前任务附近的持续提示 | 用白话说明已知原因、当前结果及可执行下一步；保留原来的请求和草稿 |
| 后台任务完成或失败 | 可回查的任务状态与运行记录 | 保留结果，不抢焦点，不重复弹同一问题 |
| 影响数据或需要立即决定 | 现有可访问对话框 | 明确选项及后果；保存未确认时不能擅自刷新、关闭或丢弃输入 |
| 需要排查具体原因 | 用户手动打开详细记录 | 保留原始技术信息，普通页面不铺代码、原始协议编号或堆栈 |

错误说明覆盖“发生什么、影响哪项操作、接下来可以做什么”。数据是否已保存、操作是否已执行、是否可以重试，必须依据实际回执；结果未知不写成失败未执行，也不写成已经安全保存。未连接的可选AI功能不是全产品故障。

示例：一般的“回执未读回”应按实际状态解释为“暂时没确认这次操作是否完成，请先查看处理状态”；明确禁用且未受理的处理说明“这项处理尚未启用，本次没有开始”；已经执行但未提供回答的AI任务不能说明成“没有执行”。

## 本批实现与边界

优先复用已有React、Radix对话框、错误摘要与诊断中心，不引入第二套通知框架。六个主要消费组件把失败摘要与原始详情分开；文件处理取消、重试和结果未知的原有语义保持。Core命令与本地HTTP请求失败自动记录受限元数据，不自动弹窗或重试；重复失败合并计数，恢复或切工作区后丢弃迟到的旧请求记录。自动记录不收集请求正文、地址、凭证、路径、任意异常原文或堆栈；手动详细记录仍保留原有内容。

本批自动记录仍是当前工作区会话的最近50条，不称跨重启持久日志。启动恢复记录、未捕获页面异常、完整成功操作历史和跨重启问题记录需要另行补齐；新增错误边界不得自动卸载有未保存内容的整个工作区。实现、组件故障注入、构建、原生截图和云CI分别验收，实际结果写唯一执行记录。

参考成熟交互规则：[Fluent消息条](https://fluent2.microsoft.design/components/web/react/core/messagebar/usage)、[Fluent提示通知](https://fluent2.microsoft.design/components/web/react/core/toast/usage/)、[W3C状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。按影响选用局部提示、消息条或必须回应的对话框，并保证状态可被辅助技术读出；不是给每次异常都增加弹窗。
