## 1. UNKNOWN 与周期性对账（P2）

事实（按当前源码）：评分 claim 只在两处变成 UNKNOWN——重试路径里的 `reconcile_stale_dispatch`，以及 Core 启动时一次性终结超过 150s 的遗留 DISPATCHED（`abandon_dispatched_after_restart`）。**没有周期性后台巡检**；UNKNOWN 不会自动变成"可重试的确认失败"；也从不重新启动 worker。

| 选项 | 做法 | 影响 |
| --- | --- | --- |
| A 保持现状 | 只在重试与启动时终结 | 最保守；长时间运行的进程里遗留 claim 会一直显示 DISPATCHED |
| B 周期性只终结（建议） | Core 内定时（例如每 5 分钟）把超过窗口的 DISPATCHED 终态化为 UNKNOWN，**绝不重启 worker** | 状态更及时；仍保持"至多一次"语义 |
| C 显式运维触发 | 不常驻定时器，提供人工触发的 reconcile 命令 | 无需新后台任务；需要人手 |
| D 周期性 + 自动重试 | UNKNOWN 自动重新派发 | 会改变"至多一次"语义，风险最高，不建议无确认实施 |

**需要你确认的产品语义**：UNKNOWN 之后是否允许"用新的 `client_event_id` 重新求分"作为正式行为？B/C 都默认"不自动重试"，只提供新事件重试。

## 2. OpenMAIC 课程级入口（P1）

事实：v2 适配器只接 quiz 与文本 slide（纯色背景、无动画，媒体/图形/活动内容会被拒绝并提示保全原件）；Core 只存文档、不解析课程载荷；imported-course v1/v2 由客户端按已存 schema 分派；固定 Node worker 的真实运行有本地证据，但没有"完整多场景课程"产品链。

需要你定三件事：

1. Core 是否要做**服务端课程级校验/入口**（课程 manifest、批量场景校验），还是继续"Core 存储 + 客户端分派"？
2. 四个消费者（研究 / 学习 / 工作区 / 导出）必须接哪些、按什么顺序？
3. 真实本地模型生成什么时候进入 scene build（现在 worker 是固定/离线构造）？

建议的最小切片：先在 Core 增加**只读的课程包投影**（场景数量、类型分布、是否全部可播放），不解析内容、不做渲染；确认产品边界后再扩服务端校验。
